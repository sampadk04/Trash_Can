KPG is a knowledge graph system that transforms Standard Operating Procedure (SOP) documents into structured, searchable, and interconnected graph databases.

Core Capabilities
1. SOP Document Processing
- Extracts structured knowledge from unstructured SOP text documents

2. Hierarchical Knowledge Structure
The system creates a 4-layer hierarchy:
- Episodic Nodes: Source SOP documents with summaries
- Primary Tasks: High-level scenarios/procedures (e.g., "Change Billing Cycle")
- Atomic Subtasks: Reusable procedural units that can be shared across multiple primary tasks
- Action Steps: Individual step-by-step instructions within each subtask

3. Graph Database Architecture
- Stores all extracted knowledge in Neo4j graph database
- Creates relationship edges: MENTIONS, FIRST_SUBTASK, NEXT_SUBTASK, FIRST_STEP, NEXT_STEP

- Enables querying and traversal of procedural knowledge

4. Intelligent Search
Implements 3-layer hierarchical search:
- Layer 1: Searches episodic nodes (source documents)
- Layer 2: Searches primary tasks within relevant episodes (parallel)
- Layer 3: Gathers complete context with recursive dependency resolution
 
Supports multiple search strategies:
- Fulltext search
- Semantic search (using embeddings)
- Hybrid search
- Cross-encoder reranking
- MMR (Maximal Marginal Relevance) for diverse results

5. Key Features
- Embedding-based semantic search using OpenAI embeddings
- JSON persistence for extracted structures
- Cross-episode connections to link related procedures
- Reflection mechanism for iterative extraction quality improvement
- Context gathering with recursive dependency resolution
- Reranking capabilities for improved search relevance

## Overview

The Voice Bot Collections system is a real-time conversational AI framework designed for IDFC First Bank's EMI collection operations. The system handles reminder calls, payment confirmation calls, and negotiation with customers who have missed their EMI payments.

### Key Features
- **Real-time Conversational AI**: Dynamic, context-aware conversations with customers
- **Multi-lingual Support**: Hindi and English (primarily Hinglish for natural conversations)
- **Personalized Interactions**: Customer-specific data drives conversation context
- **Structured Flow**: Pre-defined conversation stages with intelligent routing
- **Automated Disposition**: Post-call classification and intent extraction

## System Architecture

### High-Level Architecture Flow

```
┌─────────────────────────────────────────────────────────────────┐
│                    REAL-TIME CALL FLOW                          │
└─────────────────────────────────────────────────────────────────┘

1. Customer Profile + Context Data
           ↓
2. LLM (Text Generation)
   - Generates personalized bot response
   - Uses customer config + conversation history
           ↓
3. TTS (Text-to-Speech)
   - Converts generated text to speech
   - Fast conversion for real-time interaction
           ↓
4. Bot speaks to customer
           ↓
5. Customer responds
           ↓
6. STT (Speech-to-Text)
   - Converts customer speech to text
           ↓
7. Customer response text → LLM (as context)
           ↓
8. Loop continues until call completion

┌─────────────────────────────────────────────────────────────────┐
│                    POST-CALL PROCESSING                         │
└─────────────────────────────────────────────────────────────────┘

9. Complete Transcript
           ↓
10. Disposition Engine (LLM-based)
    - Classifies call outcome
    - Extracts customer intent
           ↓
11. Update Customer Configuration
    - Update parameters based on disposition
    - Prepare for next interaction
```

### Core Components

1. **LLM (Large Language Model)**
   - Generates contextual, personalized responses
   - Receives customer profile, conversation history, and current node context
   - Follows strict prompts for each conversation stage

2. **TTS Engine (Text-to-Speech)**
   - Fast conversion for real-time interaction
   - Supports gender-specific voices (male/female)
   - Maintains natural Hinglish pronunciation

3. **STT Engine (Speech-to-Text)**
   - Converts customer speech to text
   - Handles code-mixed language (Hinglish)

4. **Disposition Engine**
   - LLM-based classification system
   - 15 distinct disposition categories
   - Updates customer configuration for next call

## Conversation Flow & Node Structure

### Node-Based Architecture

The conversation follows a **multi-node architecture** where each node represents a distinct stage of the conversation with specific objectives and capabilities.

```
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│   Node 1     │ ───► │   Node 2     │ ───► │   Node 3     │
│ AUTHENTICATE │      │  NEGOTIATE   │      │  ONCALL PAY  │
└──────────────┘      └──────────────┘      └──────────────┘
```

### Node 1: Authentication (`authenticate`)

**Objective**: Confirm customer identity before proceeding with collection discussion.

**Key Characteristics**:
- **Prompt File**: `prompt_authenticate.txt`
- **Primary Goal**: Verify the person on call is the actual customer
- **Initial Message**: Gender and language-specific greetings
  - Example (Hindi, Female): "Good Morning! मैं IDFC First Bank से {bot_name} बोल रही हूँ। क्या मेरी बात {customer_name_hinglish} जी से हो रही है?"

**Available Actions**:
- `CustomerAuthenticatedVocodeActionConfig()`: Called when identity confirmed
- `TerminateCallVocodeActionConfig()`: End call if wrong number/voicemail

**Decision Logic**:
```
Customer confirms identity?
├─ YES → Call action_customer_authenticated
│        → Transfer to Node 2 (negotiate)
│
└─ NO → Determine call receiver relationship
       ├─ Family/Friend → Leave message, terminate
       ├─ Wrong Number → Inform, terminate
       ├─ Voicemail → Leave message, terminate
       └─ Customer Deceased → Document, terminate
```

**Guardrails**:
- Never reveal loan details before identity confirmation
- Handle ambiguous responses with re-confirmation
- Smart detection of inconsistencies and deflection attempts

---

### Node 2: Negotiation (`negotiate`)

**Objective**: Negotiate with authenticated customer to collect payment.

**Key Characteristics**:
- **Prompt File**: `prompt_negotiate.txt` (varies by escalation flag and payment type)
- **Primary Goal**: Convert payment intent into actual payment
- **Context**: Requires session conversation history
- **Escalation Variants**:
  - Standard negotiation (regular follow-up)
  - Escalatory negotiation (senior officer tone for persistent defaults)

**Available Actions**:
- `GuideOncallPaymentVocodeActionConfig()`: Transfer to on-call payment guidance
- `ValidatePTPDateVocodeActionConfig()`: Validate promise-to-pay dates
- `SendPaymentLinkVocodeActionConfig()`: Send/resend payment link
- `SendDeepPaymentLinkVocodeActionConfig()`: Send UPI deep link (fallback)
- `SetEmiOfferVocodeActionConfig()`: Initiate negotiation for partial payment (only when `total_vs_emi_flag` = False)
- `TerminateCallVocodeActionConfig()`: End conversation

**Payment Type Logic** (`total_vs_emi_flag`):
```
total_vs_emi_flag = True (EMI-First Escalatory)
├─ Focus: Collect single EMI amount only
├─ Prompt: prompt_negotiate_escalatory_emi_*.txt
└─ Action: SetEmiOfferVocodeActionConfig EXCLUDED

total_vs_emi_flag = False (Total Payment Negotiable)
├─ Focus: Collect total payable amount (negotiable)
├─ Prompt: prompt_negotiate_escalatory_total_*.txt
└─ Action: SetEmiOfferVocodeActionConfig INCLUDED
```

**Core Negotiation Scenarios**:

1. **Immediate Payment Intent**
   - Customer agrees to pay now
   - Action: Send payment link via WhatsApp/SMS
   - Offer: Real-time on-call payment guidance (if customer hesitant)

2. **Technical Issues with Payment**
   - Link not received/expired/not opening
   - Action: `action_send_payment_link` (resend/troubleshoot)
   - Fallback: UPI deep link if standard link fails

3. **Promise to Pay (PTP)**
   - Customer commits to pay at future date
   - Action: `action_validate_ptpdate` (validate and log)
   - Classification: PTP (≤3 days) or FPTP (>3 days)

4. **Financial Objections**
   - Customer disputes charges or offers partial payment
   - Action: `action_set_emi_offer_flag` (initiate negotiation)
   - Response: Conditional rebuttal or offer acceptance

5. **Refusal/Disputes**
   - Customer refuses to pay or raises disputes
   - Response: Document intent, provide customer care contact
   - Action: Terminate with appropriate disposition

**Smart Router Protocol**:
- **Tool-First Mandate**: Check for tool triggers before generating response
- **Intent Over Sequence**: Customer's latest intent overrides flow sequence
- **No Conversational Inertia**: Don't continue predefined flow if intent changes

---

### Node 3: On-Call Payment (`oncall_payment`)

**Objective**: Guide customer through live payment process on the call.

**Key Characteristics**:
- **Prompt File**: `prompt_ocop.txt`
- **Primary Goal**: Convert high payment intent to successful transaction
- **Initial Message**: "Please जो secure payment लिंक आपको WhatsApp या SMS पे भेजा गया है, उसे click करें"
- **Role**: Payment Closer (not negotiator)

**Available Actions**:
- `SendPaymentLinkVocodeActionConfig()`: Resend link if needed
- `SendDeepPaymentLinkVocodeActionConfig()`: UPI fallback
- `CheckPaymentStatusVocodeActionConfig()`: Verify payment completion
- `TerminateCallVocodeActionConfig()`: End after payment/failure

**Payment Guidance Flow**:
```
1. Link Access
   ├─ Customer clicks link → Guide through webpage
   ├─ Link not received → Resend immediately
   └─ Link not opening → Troubleshoot/fallback to UPI

2. Payment Method Selection
   ├─ UPI → Guide UPI ID entry
   ├─ Card → Guide card details entry
   ├─ Net Banking → Guide bank selection
   └─ Wallet → Guide wallet selection

3. Payment Execution
   ├─ Customer confirms attempt → Check payment status
   ├─ Technical error → Troubleshoot or escalate
   └─ Bank-side issue → Direct to customer care

4. Confirmation
   ├─ Payment successful → Confirm, thank, terminate
   └─ Payment failed → Document reason, provide alternatives
```

**Problem Triage Protocol**:

**Category 1: Link Issues (Bot Solvable)**
- Link not received, expired, not opening, error messages
- Action: `action_send_payment_link` or `action_send_deep_payment_link`

**Category 2: Banking Issues (Unsolvable)**
- Low balance, daily limit exceeded, frozen account
- Action: Acknowledge, direct to customer care, terminate

**Payment Solution Hierarchy**:
1. **Primary**: Secure payment link (SMS/WhatsApp)
2. **Fallback**: UPI deep link (with explicit consent)
3. **Alternative**: Friend/family payment (forward link)
4. **Escalation**: Customer care contact

### Node Transition Logic

```python
# From node-traffic-flow.py

    onEndTransferToNode: 2  # Always transfers to negotiate

Node 2 (negotiate)

**Session Context Requirements**:
- **Node 1**: No context required (fresh start)
- **Node 2**: Requires session conversation (history from Node 1)
- **Node 3**: No previous context required (focused on payment only)

## Disposition Classification

### Overview

After each call, the complete transcript is analyzed by a **Disposition Engine** (LLM-based) to classify the call outcome and extract customer intent. This classification drives future interactions and campaign strategy.

**Source**: `vbc-l1-disposition-prompt.md`

### 15 Disposition Categories (Priority Order)

The disposition engine evaluates in **strict priority order** - the first matching category wins:

#### 1. **CPD - Claims Paid For Dues**
- **Pattern**: Customer claims payment already made (before the call)
- **Example**: "मैंने तो payment कर दिया था, bank ने update नहीं किया"
- **Action**: Verify payment status, update records

#### 2. **ONP - Collect Online Payment (Live on Call)**
- **Pattern**: Customer initiated payment **during the call** with agent guidance
- **Criteria** (ALL 4 must be true):
  - Customer explicitly agreed to pay on call
  - Link was sent during call
  - Customer attempted payment process
  - Outcome confirmed (success or technical failure)
- **Note**: If technical issue prevented payment but intent was clear → Still ONP

#### 3. **PTP - Promise to Pay (≤ 3 days)**
- **Pattern**: Customer explicitly promises payment within 3 days
- **Examples**: "आज शाम को करूंगा", "tomorrow", "कल"
- **Action**: Schedule follow-up, validate date

#### 4. **FPTP - Future Promise to Pay (> 3 days, within month)**
- **Pattern**: Strong commitment but date >3 days away or unspecified
- **Examples**: "salary आने पर", "28 तारीख तक", "definitely करूंगा"
- **Action**: Schedule month-end follow-up

#### 5. **DIR - Dispute Raised**
- **Pattern**: Customer disputes loan, claims fraud, product/service issues
- **Examples**: "मैंने loan लिया ही नहीं", "fraud है ये", "AC ही नहीं मिला"
- **Action**: Escalate to dispute resolution team

#### 6. **RTP - Refuse To Pay**
- **Pattern**: Acknowledges dues but refuses payment (this month)
- **Examples**: "नहीं करूंगा payment", "next month में दूंगा", "charges remove करो पहले"
- **Action**: Note refusal, schedule escalatory follow-up

#### 7. **LDD - Lien/Auto Debit/Payment Issue**
- **Pattern**: Technical payment processing issues (not intent-related)
- **Examples**: Auto-debit bounce, lien issues, UPI timeout
- **Exception**: If customer was paying on call and faced tech issue → ONP (not LDD)

#### 8. **CDE - Customer Expired**
- **Pattern**: Customer deceased, family member handling
- **Example**: "उनकी death हो गई है, certificate लेकर branch जाऊंगा"
- **Action**: Document, request death certificate, insurance claim

#### 9. **WNR - Wrong Number**
- **Pattern**: Wrong person contacted, doesn't know customer
- **Example**: "मैं अमित नहीं हूँ", "ये number मेरा है, banking नहीं लिया"
- **Action**: Update contact number, remove from campaign

#### 10. **LMS - Left Message**
- **Pattern**: Customer absent, message left with family/friend
- **Example**: "वो बाहर गए हैं, आने पर बता दूंगा"
- **Action**: Schedule callback

#### 11. **LBR - Language Barrier**
- **Pattern**: Communication issues due to language
- **Example**: "हिंदी नहीं आती, बंगाली में बात करो"
- **Action**: Route to appropriate language agent

#### 12. **CBK - Call Back (Explicit Request)**
- **Pattern**: Customer explicitly requests callback at specific time
- **Example**: "मैं driving कर रहा हूँ, 1 घंटे बाद call करो"
- **Exception**: Callback due to language → LBR (not CBK)

#### 13. **CHP - Call Hang Up**
- **Pattern**: Call disconnected before identification
- **Example**: Repeated "hello" exchanges, immediate hang up, voicemail
- **Action**: Retry at different time

#### 14. **PPC - Probable Problematic Customer**
- **Pattern**: Rude, aggressive, abusive behavior
- **Action**: Flag account, special handling required

#### 15. **OTH - Other**
- **Pattern**: Doesn't fit any above category or insufficient information
- **Action**: Manual review

### Disposition Evaluation Rules

**Process**:
1. Read transcript carefully
2. Check each disposition **in priority order**
3. Apply **first matching** disposition
4. Cite specific transcript lines as evidence
5. Reflect on answer for accuracy

**Key Principles**:
- **Intent over technicality**: Focus on primary purpose of call
- **Explicit evidence**: Cite actual transcript lines
- **No assumptions**: If unclear → OTH
- **Priority order matters**: Earlier dispositions take precedence

### Post-Disposition Actions

**Configuration Updates**:
```
Disposition → Update Fields
├─ ONP/CPD → Mark payment_received, update follow-up date
├─ PTP/FPTP → Set promise_date, callback_scheduled
├─ DIR → Set dispute_flag, escalation_required
├─ RTP → Set refusal_count++, escalation_flag
├─ WNR → Mark invalid_number, remove from campaign
└─ LBR → Update language_preference, route to new agent
```

**Campaign Strategy Adjustments**:
- Multiple RTP → Trigger escalatory mode
- Multiple CBK/LMS → Optimize call timing
- PTP not honored → Increase follow-up frequency

   │  │  └─ action_check_payment_status
   │  │

│ STAGE 3: POST-CALL PROCESSING                                   │

7. Generate Complete Transcript
   ├─ Compile all bot-customer exchanges
   └─ Format with speaker labels (Bot/User)

8. Disposition Classification
   ├─ Send transcript to Disposition Engine (LLM)
   ├─ Context: vbc-l1-disposition-prompt.md

   ├─ Based on disposition:
   │  ├─ Update payment status
   │  ├─ Set follow-up dates
   │  ├─ Increment counters (refusal_count, etc.)

    ├─ Analyze disposition trends
    ├─ Adjust call timing/frequency
    ├─ Determine escalation requirement

## Technical Implementation

### Prompt Engineering Best Practices

**1. Gender Guardrails**
- **Bot Gender**: Fixed (determined by `speaker_gender`)
  - Female: "मैं आपकी मदद कर **रही हूँ**"
  - Male: "मैं आपकी मदद कर **रहा हूँ**"
- **Customer Gender**: Always neutral (use plural forms)
  - Correct: "आप कर **सकते हैं**" (gender-neutral)
  - Forbidden: "आप कर **सकती हैं**" (assumes female)

**2. Tool-First Mandate**
- Check for tool triggers before generating response
- Tool calls are silent (never mentioned to customer)
- Example: Customer says "link नहीं मिला" → Immediately call `action_send_payment_link` (don't just say "I'll send it")

**3. Smart Router Protocol**
- **Intent Over Sequence**: Latest user intent overrides predefined flow
- **No Conversational Inertia**: Don't continue flow if intent changes
- Example: During negotiation, if customer says "I want to speak to manager" → Route to escalation, don't continue payment pitch

**4. Conversational Naturalness**
- **Hinglish Mix**: Hindi for everyday words, English for technical terms
  - ✅ "आपका EMI payment pending है"
  - ❌ "आपका किश्त भुगतान लंबित है" (too formal)
- **Fillers**: Use natural acknowledgments ("अच्छा", "ठीक है", "समझ गई")
- **Avoid Formal Hindi**: Don't use literary words like "भुगतान", "सम्पर्क"

**5. Structured Outputs**
- Most responses: Natural dialogue only
- Exception (Scenario 5.2): Structured format for summarization
  ```
  SUMMARY_START: [Brief call summary]
  NEXT_RESPONSE: [Next spoken text]
  ```

```python
def parse_llm_response(response):
    # Check for action calls (internal format)
    action_match = re.search(r'ACTION_CALL: (\w+)', response)
    if action_match:
        action_name = action_match.group(1)
        execute_action(action_name)
    
    # Extract spoken text (everything except action calls)
    spoken_text = re.sub(r'ACTION_CALL:.*', '', response).strip()
    
    return spoken_text, action_name
```

# NEW FRAMEWORK: Customer State Graph

I want to start with a basic framework.
We will have 4 types of nodes/entities in the graph:
1. Customer
2. Conversation/Call
3. Disposition
4. Insight

For edges we will have:
1. Customer -> HAS -> Conversation 
2. Conversation -> NEXT -> Conversation
3. Conversation -> LEADS_TO -> Disposition
4. Customer -> RELEVANT -> Insight

Example:
This is how the basic structure of the graph will look like for one customer with two calls.

Start: 
Build Customer Node from customer configuration data.

Insert Call 1: 
Create corresponding Conversation Node, and attach and it's corresponding Disposition Node.

Extract any strong insights from Call 1 and attach to Customer Node as Insight Node. (Note: This Insight Node stores which call (s) it was derived from)

Insert Call 2:
Create corresponding Conversation Node, and attach and it's corresponding Disposition Node.

Connect Call 1 and Call 2 using NEXT edge.

Extract any strong insights from Call 2, check for duplication and contradiction with the existing Insight Nodes attached to Customer Node.
Cases:
- If no duplication or contradiction, attach new Insight Node to Customer Node.
- If duplication/minor update to an existing Insight Node, update existing Insight Node to reflect both calls.
- If contraction to an existing Insight Node, update it by changing the is_expired attribute to true, and create a new Insight Node with the updated insight.

Initially we want to augment the context during the negotiations phase using a Customer State Graph. We can directly decide what actions to be taken based on the state of the customer in the graph. For example, notice that in the negotiation system prompt, we are mapping out '| Disposition Code | Customer's Situation | Your Conversational Goal | Tone to Adopt |' matrix in the prompt.
Our graph will fetch the latest disposition related information from the last call and the relevant customer insights to help bot drive the conversation in a more personalized manner.

We want to use this Customer State Graph as context for future calls to make the conversation more personalized and effective.

We want this to be a personalized context that captures customer preferences, intents, nuances over multiple calls.

We want to also update this Customer State Graph after every call based on various analysis.
Notice that each customer may have multiple calls over time. We should be able to maintain previous conversations as separate nodes with it's own attributes and chain them chronologically. And we should be updating the Customer State Graph after every call. Each customer can be thought of a separate node. The Customer State Graph should be a super-set of disposition analysis, more generic, capturing details about customer preferences and other nuances.
